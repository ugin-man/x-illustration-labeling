# 本番運転の監視手順（草案・開始待ち）

この文書は準備用であり、監視の開始、定期実行、担当者への連絡を指示するものではない。統括から開始指示を受けるまで待機する。監視はメタデータのみを対象とし、分類画像、元 ZIP、除外された投稿、画像検索結果、人間用スクリーニング画面を開かない。分類、再分類、担当者の新規作成、他担当の結果修正、隊列ブランチの直接編集は行わない。

## 開始時に統括から受け取る情報

- 対象の固定 run config と run ID、10担当のスレッド ID と各 worker ID の対応。
- 現在有効な明示的な本番・監視開始許可と、停止指示の受け取り方。
- Git 上の未完了件数、予約状況、checkpoint および集約状態を取得するための、対象 run に適合した読み取り手順。
- スレッドの状態を確認し、許可された継続メッセージを送る方法。
- 集約検証の実行者・結果の受け取り方、および統括への報告先。

不足、対応の不一致、情報の取得不能があれば推測して操作せず統括に報告する。モデル指定の根拠は担当作成時の `gpt-6.1-terra/high` であり、内部モデル名の自己判別を起動条件にしない。

## 監視の流れ

1. 開始許可と対象を確認し、指定された読み取り手順で固定 run の Git 上の未完了・予約・checkpoint と10担当の実際のスレッド状態を確認する。画像や投稿本文を開かない。
2. 以後おおむね1時間ごとに同じ確認を行う。通常の担当者は最大50投稿を終えた後、自律的に次を取得する。監視はその保険であり、稼働中の担当者に不要な割り込みを入れない。待機中も新しい停止指示に応答できる方法を用いる。
3. 未完了の作業があり、対象担当のスレッドが停止または終了していることを確認できた場合のみ、その担当自身に下記の継続指示を送る。固定 run、対応する worker ID、既存 checkpoint を使う。状態が不明な場合は停止とみなさず、確認または統括への報告を優先する。
4. 送信後は結果と状態の変化を確認し、時刻、対象、根拠となったメタデータ、送信結果を記録する。実行中に重複送信しない。同じ停止状態への反復送信で無限再起動せず、再開できない場合は原因を統括に報告する。
5. 空き作業がすべて他担当に予約されている場合、または対象が完了済みの場合は再起動しない。取得できる空きがあるか不明なら推測せず確認する。利用上限、認証問題、サービス停止、明示的な人間の停止指示を回避しない。
6. `unresolved_posts == 0` は全投稿がcheckpointされた状態であり、全区分のfinishを意味しない。停止担当が全投稿保存済み・未finishの区分を持つ場合も、その区分の完了処理へ再開させる。`all_jobs_completed` と各区分のcompleted状態を確認する。未完了件数がゼロに見えても、監視担当が独断で全量完了としない。投稿 ID を基準に完成と正規除外を集約検証した結果を統括に確認してもらう。検証待ちや監視終了の判断待ちとして報告する。

## 継続指示のひな形

> 固定 run `{run_id}` を、あなた自身の worker ID `{worker_id}` と既存 checkpoint から再開してください。既存の run config と運用上の制約に従い、最大50投稿ずつ取得して作業を続けてください。空きが他担当にすべて予約済み、作業完了、認証・利用上限・サービス障害、または人間の停止指示がある場合は無理に続行せず、その状態を報告してください。

送信前に対象スレッドと worker ID の対応、最新の許可、実際の停止状態、未完了と予約状況を再確認する。実際の run の正規手順と矛盾する場合はひな形をそのまま送らず、統括に確認する。
