# 本番運転の監視手順

ユーザーは、本番担当が自律継続する通常運転に加え、このPCのTerra監視担当による約1時間ごとの確認と、停止担当への再開メッセージを保険として許可した。実際の開始は統括の明示的な開始指示を受けてからとし、対象は `review/production-v4-001_launch.json` の10担当と固定runだけ。監視はメタデータのみを対象とし、分類画像、元 ZIP、除外された投稿、画像検索結果、人間用スクリーニング画面を開かない。分類、再分類、担当者の新規作成、他担当の結果修正、隊列ブランチの直接編集は行わない。

## 開始時に統括から受け取る情報

- 対象の固定 run config と run ID、10担当のスレッド ID と各 worker ID の対応。
- 現在有効な明示的な本番・監視開始許可と、停止指示の受け取り方。
- Git 上の未完了件数、予約状況、checkpoint および集約状態を取得するための、対象 run に適合した読み取り手順。
- スレッドの状態を確認し、許可された継続メッセージを送る方法。
- 集約検証の実行者・結果の受け取り方、および統括への報告先。

不足、対応の不一致、情報の取得不能があれば推測して操作せず統括に報告する。モデル指定の根拠は担当作成時の `gpt-6.1-terra/high` であり、内部モデル名の自己判別を起動条件にしない。

## 監視の流れ

1. 開始許可と対象を確認し、指定された読み取り手順で固定 run の Git 上の未完了・予約・checkpoint と10担当の実際のスレッド状態を確認する。画像や投稿本文を開かない。
2. 以後おおむね1時間ごとに同じ確認を行う。通常の担当者は最大50投稿を終えた後、自律的に次を取得する。監視はその保険であり、稼働中の担当者に不要な割り込みを入れない。待機中も新しい停止指示に応答できる方法を用いる。
3. 未完了の作業があり、対象担当のスレッドが停止または終了していることを確認できた場合のみ、その担当自身に下記の継続指示を送る。固定 run、対応する worker ID、既存 checkpoint を使う。状態が不明な場合は停止とみなさず、確認または統括への報告を優先する。
4. 送信後は結果と状態の変化を確認し、時刻、対象、根拠となったメタデータ、送信結果を記録する。実行中に重複送信しない。同じ停止状態への反復送信で無限再起動せず、再開できない場合は原因を統括に報告する。
5. 空き作業がすべて他担当に予約されている場合、または対象が完了済みの場合は再起動しない。取得できる空きがあるか不明なら推測せず確認する。利用上限、認証問題、サービス停止、明示的な人間の停止指示を回避しない。
6. `unresolved_posts == 0` は全投稿がcheckpointされた状態であり、全区分のfinishを意味しない。停止担当が全投稿保存済み・未finishの区分を持つ場合も、その区分の完了処理へ再開させる。`all_jobs_completed` と各区分のcompleted状態を確認する。未完了件数がゼロに見えても、監視担当が独断で全量完了としない。投稿 ID を基準に完成と正規除外を集約検証した結果を統括に確認してもらう。検証待ちや監視終了の判断待ちとして報告する。

## 継続指示のひな形

> 固定 run `{run_id}` を、あなた自身の worker ID `{worker_id}` と既存 checkpoint から再開してください。既存の run config と運用上の制約に従い、最大50投稿ずつ取得して作業を続けてください。空きが他担当にすべて予約済み、作業完了、認証・利用上限・サービス障害、または人間の停止指示がある場合は無理に続行せず、その状態を報告してください。

送信前に対象スレッドと worker ID の対応、最新の許可、実際の停止状態、未完了と予約状況を再確認する。実際の run の正規手順と矛盾する場合はひな形をそのまま送らず、統括に確認する。

## 実際の監視先と取得手順

- 固定run：`production-v4-001`、コードcommit：`4d2c98374a1364faf1e2b546a4c460e80e9b2903`。
- worker対応と統括・監視のchat ID：`review/production-v4-001_launch.json`。
- GitHub：非公開 `ugin-man/x-illustration-labeling`。
- queue index参照：`refs/heads/codex/jobs/production-v4-001/dispatch-index`。
- GitHub連携のfetchで上のrefのheadを取得し、その**固定commit**の `state.json` を取得する。rawファイルURLでref名を曖昧に連結するより、取得したcommit SHAを使う。index未作成の初期状態を完了と解釈しない。
- indexは手元のprivate領域に保存して `python -X utf8 ops/watch_snapshot.py --config runs/production-v4-001.json --state PRIVATE_STATE_FILE` で整合性確認と要約を行う。run/catalog/workerの不一致は停止して報告する。内部tokenをチャットや公開報告へ出さない。
- スレッド確認は `wait_threads` の `timeoutMs: 0` を優先し、10担当を8件と2件へ分ける。前回cursorを保存する。初回・不明点・終了理由確認だけ `read_thread` を使用し、研究画像は開かない。
- 本番の開始メッセージを受けた後、おおむね3600秒ごとに確認する。現在のチャット内で継続し、1回55秒以内の待機を組み合わせる。特定ジョブの完了監視用にapp automationやOSスケジュールを新規作成しない。
- 毎回同じ状態をユーザーへ通知しない。再開、失敗、完了、ユーザー対応が必要な変化だけを記録・報告する。監視記録は `private/production-watch/` に残す。

## 再開してよい状態

実際のチャットがidle/completed等で終了し、本人の未finish区分がある、または取得可能な区分がある場合。未finish区分の全投稿がcheckpoint済みでもfinish処理が必要なので再開対象となる。実行中の担当へ「続けて」を重ねて送らない。必要な承認・入力待ちは勝手に解消しない。全区分が他担当に予約中なら空き待ち担当を再開しない。

再開前に最新状態を再確認し、対象ごとに送信時刻・理由・head・turn IDを記録する。同じ停止状態に繰り返し送信せず、送信済みでも進捗が戻らない場合は統括へ報告する。利用上限・認証・サービス停止・人間の停止指示を無視する再開はしない。活動中なのに長時間checkpointが進まない場合は、稼働中を停止済み扱いせず統括へ状況を報告する。

本文取得APIの個別投稿に対するHTTP 401/403/404やタイムアウトを、GitHub・モデル全体の認証停止と混同しない。`context fetch` が終了コード0、`state: technical_failure` で返した個別本文の失敗は、既存分類マニュアルに従って本文欄の取得失敗として保存し、観測できた画像属性を残して次へ進むケース。同じ本文の再取得・ログイン・別サービスによる制限回避はしない。個別本文失敗だけで停止した担当は、失敗元とCLI結果を確認したうえで通常の再開対象にできる。

全413区分がcompletedになったら、統括へ集約検証を依頼する。監視はユーザーの停止、統括からの検証済み完了、または継続不能の具体的理由が確認されるまで継続する。監視自身が終了してしまえば自動送信も止まるため、終了したのに監視中とは報告しない。
