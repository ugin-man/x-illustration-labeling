# ops-r3: 停止原因と復旧の検証

2026-11-14。ユーザーは停止6担当の復旧、保留競合の根本修正、全10担当が実処理して保存することの確認を指示した。サブエージェントは禁止。親が直接コードを修正し、既存Cloudの10担当へ連絡する。

## 原因

1. **2件目の保留に既存保留を含めていた。** r2のdeferは、新しい保留を加えた全blocked集合から受理済みだけを除き、過去の保留もsync_contextへ渡した。再処理禁止guardが正しく拒否するため、新しい別投稿を保留できなかった。合成データの逐次deferテストで同じConflictを再現した。
2. **成功結果とロック後処理の失敗が混ざった。** 通常コマンドが結果を返した後の短時間gate解放で通信失敗すると、全操作が失敗したように見えた。r3は元の結果・例外を維持し、後処理の警告を分離する。gateは削除・強奪せず自然失効を待つ。
3. **取得元の失敗と作業基盤の障害が曖昧だった。** 09は本文404の3連続を全体停止理由にした。新運用では本文取得失敗を正しく記録し、画像・検証・保存が動くなら継続する。本文再取得や架空の成功記録は許可しない。
4. **08の再試行は自動承認審査に拒否された。** 旧停止条件の下で同じGitエラー後の3回目nextが拒否された。今回のユーザー指示に基づく読み取り専用statusを1回確認し成功。受理29件、所有期限切れを確認した。拒否されたnextの別経路実行はしていない。

## 修正範囲

- 独立したops_runtime_r3と新運用manual。固定分類run、r2コードとmanifest、除外30投稿、受理済み回答を変更しない。
- 新しく保留する連結成分だけを同期・保全する。既存保留へのdeferは再表示せず未完了保留として応答する。
- r2の保留・監査記録を互換読取りし、過去の保留を解除しない。
- 一時的なGit読み取り通信失敗だけ最大3回。認証・利用制限・未知の失敗は自動再試行しない。pushは盲目的に再試行しない。
- ローカルの同一workerロックは旧版と共通にし、別revisionで二重書込みを許さない。

全10担当で、固定isolationと新nextの照合、通常の未処理2投稿の実画像表示、save、checkpointを確認する。保留・暫定除外だけの増分はこの2件に数えない。親がGitHubと実ツールイベントを照合し、既存293回答のhash不変と重複予約なしを検証する。指示の受領やステータスactiveだけを成功証拠にしない。

01・03・05・06は失敗したdeferの投稿IDを既存記録で特定済み。画像を再表示せずメタデータ保留を先に完了し、別の通常投稿へ進む。
