# 一時アクセス応答の復旧

2026-11-14。既存10担当を直接操作して検証。サブエージェントは使用していない。

r4では旧未送信11投稿を回収し、新規3投稿も共有保存できた。一方、複数担当が同時に `Git fetch/ls-remote failed: access (bounded attempts=1)` で停止した。07は受理照会ができず `acceptance_indeterminate` で停止した。画像の再表示や受理済みデータの変更はしていない。

同じ認証・同じリポジトリを使う新しい読み取り診断は02・04・06のすべてで成功した。旧エラーは詳細をまとめていたため、元のHTTPコードやサーバー側の原因は確定できない。HTTP応答だけで恒久的な権限欠如と扱って終了する分類を改めた。

r5はHTTP 401/403応答に対し、同じ資格情報のまま間隔を空け最大10回再確認する。429、明示的なレート制限、Retry-After、解除時刻を扱い、指定時刻前に要求を繰り返さない。一般的な待機方針の参考は [GitHubの公式案内](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api#handle-rate-limit-errors-appropriately)。Gitの元の障害がAPIレート制限だったと断定するものではない。

受信ヘッダーは内部で捕捉し、応答コードと待機秒数だけを返す。URL、認証情報、Cookie、生ヘッダーは返さない。待機ログはstderrへ出し、標準出力のJSONを壊さない。実際の承認審査拒否は通信エラーとは別に扱い、拒否された操作を再実行しない。

push失敗時は先に受理を照会する。同じcommitが受理済みなら成功として続行する。未受理かつ対象refが不変の場合だけ同一commitを再送する。認証情報・接続先の変更、force push、受理済み回答の変更はしない。

r5開始前の共有保存は5,468件。全jobのheadと、再開対象10jobの197件の投稿blob SHAを保全した。元のr4開始前5,454件も、該当183件の完全一致と他jobのhead不変により保全を確認した。32件の修正箇所テストを通して実機再開し、全体回帰テストを並行実行した。最終成否と実閲覧イベントの証拠は別の検証JSONへ記録する。

補助報告branchの一時障害だけでは、正常な分類・queue保存まで止めない。毎時送信係は送信だけを担当し、コード切替中は既存automationを一時停止している。検証後にr5の定型文で再開する。
