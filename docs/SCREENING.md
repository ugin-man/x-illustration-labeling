# 全画像の事前確認

`全画像の事前確認を開く.cmd` をダブルクリックするか、`python -m pipeline.screening_app --open` を実行する。http://127.0.0.1:8767 で動作する。初回は開始画面だけ表示し、「画像一覧を開く」を押すまで画像を読み込まない。外部への画像アップロード、AIへの画像入力、分類API呼出しは行わない。

一覧は20,758投稿・26,612画像参照。投稿内の全画像を並べて表示する。全体番号は投稿IDで並べた固定順で、旧100投稿ツールの番号とは異なる。パイロット対象には旧番号も添える。元のZIPや旧SQLiteは書き換えず、画像は必要なものだけローカルZIPから読み、ハッシュを検査してブラウザへ渡す。

1. 投稿ごとに「対象にする」「除外」「保留」を選ぶ。理由は画面上部の選択肢から選べる。露骨な内容の説明や画像のチャット添付は不要。
2. 除外は投稿全体に適用する。直接除外した投稿の画像と同じSHA-256を含む別投稿も連動除外する。連動元の除外を解除すると、連動対象は元の確認状態へ戻る。
3. ページを見終えたら「このページの残りを対象にして次へ」を使える。画像がまだ画面に表示されていない未確認投稿が残る間は押せない。除外・保留は一括で対象へ戻さない。
4. 「直前の操作を戻す」で最後の単独・一括操作を戻せる。既存の除外は自動的に成人向けと見なさず、「旧アプリで除外」の絞り込みで別途確認できる。
5. 未確認・保留を解消したら「事前確認を完了する」で件数を確認し、確定する。これによって本番が自動開始することはない。

確認結果は `private/screening/data-v1.sqlite3` に保存する。旧アプリのDBとは別。確定時に `private/screening/screening-receipt.json` も出力する。途中でも「除外・確認結果を書き出す」でJSONを保存できる。途中のJSONには確定した採用一覧を出さない。ブラウザを閉じても保存済みの選択は残る。別の画面で更新が競合した場合は上書きせず知らせる。完了後に編集すると確認完了が解除される。

2026-11-12の隔離作業で旧data-v1と元アーカイブを作業フォルダ外の人間用保管場所へ移した。場所はignoredのprivate/human-source.jsonを人間用アプリが参照する。完了済みの全画像一覧サーバーは停止した。必要な場合だけ人が起動し、AI担当へこの一覧や原本パスを渡さない。除外30投稿・31画像は新しい配布ZIPへ含めない。

「画像を画面に表示した」という記録は、人が精査した証明ではない。確認・除外は利用者の明示操作として保存する。判別できないものは保留または除外にする。タグがないことや旧アプリで対象になっていたことを安全性の保証にしない。

## 次版と本番停止

`pipeline/contract_v3.py` と `docs/LABELING_V3.md` が新しい分類定義。旧v2のcontract/manualと100投稿の出力は変更しない。新出力は投稿全体のユニークなcharacters、画像との対応、固定3種類の体の形、色あり/無彩色を使う。主題を必須とし、背景は描き込みの段階、公式作品は一次創作へ含める。画風は削除し、任意の描写範囲は顔/胸から上/腰から上/全身/その他へ固定する。選択肢外はその他、根拠不足は判別不能とし、混合ラベルを増やさない。

確認完了後に `python -m pipeline.prepare_screened` を明示実行すると、除外を物理的に取り除いた別のZIP・catalogをローカルに作る。既存data-v1は上書きせず、共有画像ハッシュの除外も検査する。作成途中で確認結果が変わったらcatalogを有効化しない。旧data-v1を新v3へ流用しない。catalogはdata/catalogs/配下に版別に保存し、catalog-v3.jsonは最新準備版の案内として更新する。runは版別パスを固定するため、後日の確認変更で旧入力を上書きしない。

`python -m pipeline.prepare_run RUN_ID --split production` は新しいscreened catalogの存在を要求し、新runのみ作る。実行はさらに `data/launch-control.json` の別の開始許可を要求する。現在はblocked。確認完了ボタン、入力準備、run作成のいずれも、この許可を変更しない。

開始を許可する将来の手順では、ユーザーの明示した開始指示、対象run、catalog SHA-256、事前確認receipt SHA-256をlaunch-controlへ固定してから配布する。ローカルで確認結果が変更された場合は旧許可を使用できない。クラウド配布後の変更は旧runを停止し新runで扱う。今回は配布・ジョブ予約・分類を行わない。
