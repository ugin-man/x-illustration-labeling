# 運用・起動前チェック

## 固定入力

data-v1: 20,758投稿、26,612画像参照、26,357種類、416バッチ。
既存の人手回答338件（除外40件を含む）はローカルprivate/に隔離し、全対象を再評価する。
入力には画像と投稿ID・画像順のみ。人気指標と既存回答は含めない。
画像SHA-256、ZIP SHA-256、マニフェストSHA-256、分類定義・マニュアル版を固定する。

調整用100投稿、評価用100投稿、本処理用20,558投稿をseed=20261111で分離。
同一画像を共有する投稿は同じ群にまとめてから分割し、調整/評価への同一画像混入を防いだ。
近似画像の自動判定はしていない。既知の難例は調整用の追加群で確認し、評価へ混ぜない。

## 予約方式

仕事ごとに `codex/jobs/<run_id>/<job_id>` という独立ブランチを使う。
最初の予約は固有のroot commitを通常pushする。同時予約はGitHubの非fast-forward拒否で一つだけ成功する。
更新は必ず読んだheadの子commit。force pushは使わない。統括は各予約に介入しない。
60分lease、期限後2分の猶予、再予約時に新しいtokenを発行する。
古いtokenは送信できない。遠隔checkpoint済みの投稿は新担当へ引き継ぐ。
端末とGitHub/他VMの時計の大きなずれはprobeで確認する。猶予は誤差吸収であって時計同期の代替ではない。

完全な「計算の二度実行ゼロ」は保証しない。クラッシュ直前の未送信分は再処理されうる。
受理済み結果の二重採用・無言の上書きを防ぐ。異なる回答の修正は新しいreview runで行う。
push失敗を予約成功として扱わない。leaseが切れたら保存/完了は拒否する。

## Cloud capability probe（まだ起動しない）

専用Cloud環境のセットアップではPythonとGitの確認、ローカルテストだけを行う。
本番画像の分類・job予約は開始しない。設定の変更後もこの区別を守る。

ユーザーへ準備完了を報告した後、最初のTerra 1担当で下記を実証する。

1. 利用可能な画像ツールで `fixtures/vision-probe.png` を見て、文字・色・配置を報告。
   ファイル解析やOCRで答えを取得しない。期待値は統括のローカルprivate/に保存してある。
2. `git ls-remote https://github.com/ugin-man/x-illustration-labeling.git` が成功する。
3. 専用テストrunの予約→小さいJSONのcheckpoint→finishを実施し、別環境から同じ結果を読める。
   実投稿の仕事をテストデータで完了しない。
   コマンドは `python -m pipeline.probe_queue`。毎回固有のprobe runを使い、実投稿の台帳と分離する。
4. `python -m pipeline.preflight` でReleaseの1バッチだけを取得し、全hashを照合する。
5. パイロットの3投稿で全画像をモデルへ入力し、正しいJSONが保存できる。
6. 中断/再開、限定探索、モデル実行設定、実処理速度を記録する。

Cloudに画像ツールがない場合はこのCloud構成を採用しない。同じI/OをローカルCodexへ移せる。
Git push認証がなければ予約ができない。Release読取認証がなければ画像を取得できない。
この場合、APIキー等を勝手に発行せず、失敗した操作を報告して接続方法を決める。

## 拡大

1担当→2担当で実機の競合と再開を確認→調整用100件→定義を必要に応じ改版→未使用評価100件。
100件で希少属性まで保証しない。不一致は人手ラベルも含めて点検し、評価と調整を混ぜない。
本処理開始時に新しいrun設定を生成し、最初500件、その後5～10担当、必要に応じ20担当へ増やす。
本処理用設定は現時点では生成/起動しない。モデル利用枠はVMごとに独立増加するわけではない。

```sh
python -m pipeline.collect --config runs/pilot-v2-001.json --output .runtime/collected/pilot-v2-001
```

集約はダウンロード済み画像がなくてもGitの結果ブランチから行える。保存された入力manifestもhashで検証する。
出力: labels.jsonl、posts.csv、review_queue.jsonl、receipt.json。
「視覚工程を処理済み」「文脈確認済み」「技術的失敗」は別集計。
未処理画像をfalseにしない。has_red_hair等の存在フラグと、人物属性比較の分母は区別する。

## 障害対応

| 状況 | 処置 |
|---|---|
| 担当停止 | lease期限と猶予後、別担当が同じjobを予約してcheckpointから再開 |
| 予約競合 | 敗者は次のjobへ。force push禁止 |
| GitHub/networkエラー | ローカル結果を保持。新規予約を成功扱いしない。短い連続再試行をしない |
| 入力ZIP不一致 | 受理せず、jobを待機へ戻す。元ZIP/Releaseを照合 |
| 同じ投稿で回答衝突 | 先の受理済み回答を保持。新しいreview runで裁定 |
| 本文404/削除/取得失敗 | technical_failure/unknownの原因を残す。originalへ変換しない |
| 定義変更 | 新しいschema/manual/runを作る。旧回答を同じ版として混在させない |
| 利用枠待ち | 保存してrelease。新しいチャットを無制限に作り続けない |

本番runの進捗は統括のチャット記憶に依存しない。GitHubの受理済み状態を正本とする。
